### Follow-up: WebSocket terminal-error ordering on 2026-09-23

The close-code investigation reproduced a preexisting logical race in `sdk/api/handlers/openai/openai_responses_websocket_forward.go`. `ExecuteStreamWithAuthManager` publishes a terminal error to its buffered error channel before closing the error and data channels. If the consumer starts or resumes after both are ready, Go's `select` can receive the data-channel close first. The old WebSocket forwarder immediately synthesized `408 / stream closed before response.completed` and hard-closed the connection, leaving the actual 401/429 error unread. This bypassed the existing pinned-credential replay handling, so the client observed **1006 / unexpected EOF** instead of **1012 / upstream requires HTTP replay**. The same omission could discard actionable request errors or a mapped message-too-big close. This is an event-ordering defect; it does not require a memory data race or an active data writer.

- A local WebSocket regression with the error already buffered and both channels closed failed on both the unchanged `2a6daac1` production baseline and the upstream candidate, reproducing 1006 and the substituted 408 for both 401 and 429.
