### Follow-up: WebSocket terminal-error ordering on 2026-09-23

The close-code investigation reproduced a preexisting logical race in `sdk/api/handlers/openai/openai_responses_websocket_forward.go`. `ExecuteStreamWithAuthManager` publishes a terminal error to its buffered error channel before closing the error and data channels. If the consumer starts or resumes after both are ready, Go's `select` can receive the data-channel close first. The old WebSocket forwarder immediately synthesized `408 / stream closed before response.completed` and hard-closed the connection, leaving the actual 401/429 error unread. This bypassed the existing pinned-credential replay handling, so the client observed **1006 / unexpected EOF** instead of **1012 / upstream requires HTTP replay**. The same omission could discard actionable request errors or a mapped message-too-big close. This is an event-ordering defect; it does not require a memory data race or an active data writer.

Evidence and scope:

- A local WebSocket regression with the error already buffered and both channels closed failed on both the unchanged `2a6daac1` production baseline and the upstream candidate, reproducing 1006 and the substituted 408 for both 401 and 429. The initial reproducer file SHA-256 was `cdd1fa750ba00ebd75fc2369c7c88c31bb7721dc738980d6e4233689435e4501`.
- A temporary barrier in the isolated baseline let the fixture's error producer finish before forwarding its continuation. The **unchanged original replay test** then failed in **15 of 40 subcases** across 10 repetitions; all 15 failures logged a closed data channel with one error still buffered. With only the proposed forwarder repair applied and the same barrier retained, all **40 subcases** passed. The barrier and diagnostic logging were investigation-only and were not integrated. No sleep, retry, new exclusion or assertion weakening was used.
- The repair checks the existing nonblocking `handlers.PendingStreamError` helper before treating data-channel closure as EOF or success, and reuses the existing terminal-error branch. It changes one production file and adds one regression-test file. The writer/close policy, credential selection, cooldown, disabled state, lifecycle and provider boundaries remain unchanged. The original fixture has serialized writes and no upstream-disconnect subscriber; writer contention is not needed to explain this reproduction. Other intentional hard-close paths can still report 1006.

Validation of the combined upstream batch and local repair used Go **1.27.1**, macOS arm64, **CGO_ENABLED=1**, isolated worktrees and dedicated temporary caches:

- `go test -race -count=20 -json -run '^(TestForwardResponsesWebsocketPreservesPendingErrorOnClose|TestResponsesWebsocketReplaysImmediatelyAfterPinnedAuthFailure|TestResponsesWebsocketWriterCloseDoesNotWaitForActiveDataWriter|TestResponsesWebsocketGenericDisconnectDoesNotWaitForActiveDataWriter)$' ./sdk/api/handlers/openai` passed. The new regression exercises 401/429 replay, 413-to-1009 mapping, an exposed 400 request error and a silent 502 failure, with 32 ready-channel trials per case per repetition (**3,200** trials total). It also checks preservation of the original error and exactly one cancellation.
- `go test -count=1 -json -skip '^TestClaudeStandardRoundTripper(BindsLocalIP|HTTPSProxyKeepsBindAndProxyTLS)$' ./...` passed: **67** packages passed and **24** had no tests.
- `go test -race -count=1 -json` with the same two exclusions passed all **9** packages: the seven from the upstream-batch race check plus `sdk/api/handlers` and `sdk/cliproxy/auth`. No race-detector report occurred.
- `go build -o <task-directory>/test-output ./cmd/server`, formatting and `git diff --check` passed. The local bind to `127.0.0.2` again failed with `EADDRNOTAVAIL`, justifying the two existing exclusions. The optional TLS capture and three race-only allocation-budget skips remain as described above; ordinary allocation tests passed. There was no Linux run, live inference call or server operation.
